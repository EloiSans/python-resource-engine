# NoSQL stores

Resources can live in DynamoDB, Firestore or Cosmos DB. They keep the rest of
the engine: validation, hooks, state machines, row-level permissions,
tenancy, versions, events, the API and the docs. Each store has its own
limits, so its repositories declare what they can do and the engine refuses
the rest with a clear error before the query reaches the store.

```python
# DynamoDB (resource-engine-aws[dynamodb])
from resource_engine_aws import DynamoDbStore, DynamoTable

store = DynamoDbStore(
    dynamodb,
    registry,
    {
        "partners": "partners",
        "orders": DynamoTable("orders", indexes={"partner_id": "by-partner"}),
    },
)

# Firestore (resource-engine-gcp[firestore])
from resource_engine_gcp import FirestoreStore

store = FirestoreStore(
    http,
    registry,
    project="acme",
    collections={"partners": "partners"},
    sortable={"partners": ["name", "city"]},
)

# Cosmos DB (resource-engine-azure[cosmos])
from resource_engine_azure import CosmosContainer, CosmosStore

store = CosmosStore(
    database,
    registry,
    {
        "partners": "partners",
        "order_lines": CosmosContainer("order_lines", partition_key="order_id"),
    },
)

manager = ResourceManager(registry, store.unit_of_work)
```

## How each store works

| | DynamoDB | Firestore | Cosmos DB |
|---|---|---|---|
| Commit | one `TransactWriteItems` | one commit | one transactional batch per partition key |
| Atomic across | the unit of work | the unit of work | one partition |
| Writes per commit | 100 | 500 | 100 per partition |
| Lists | by key, by index (`Query`) or `Scan`, then filtered, sorted and paged in memory up to `max_items` | native `where`, `orderBy`, `offset`, `limit` and `count()` | SQL with `ORDER BY`, `OFFSET`/`LIMIT` and `COUNT` |
| Versions | condition on the version field | read in a transaction, then commit | ETag of the stored item |
| `Decimal` | number (exact) | double | double |

- **Writes wait for the commit.** `add`, `update` and `delete` are recorded in
  the unit of work and sent together by `commit`. Reads by id (`get`) see the
  operation's own writes; lists read what is committed.
- **Creates** fail if the id is taken (`VersionConflict`, `reason: already
  exists`). Ids are generated by type: random 53-bit integers for `int` ids,
  UUIDs, or 32 hex characters for `str`.
- **Too many writes** in one commit fail with `TransactionTooLarge`
  ([RE-E012](errors.md#re-e012)) and nothing is written. Move bulk changes to
  a job that commits in chunks.
- **No outbox:** these units of work don't store events. To publish events
  with the writes, keep the resources in SQL, or pair the store with a SQL
  primary in a [composite store](composite.md) (the NoSQL commit then happens
  before the SQL one).

## Capabilities

Repositories and units of work declare their limits as attributes. The
manager checks every list against them, and `capability_problems` compares
them with what the resources declare:

| Flag | On | Meaning |
|---|---|---|
| `supports_conditions` | repository | row filters (permissions, tenancy) |
| `supports_versions` | repository | compare-and-set on the version field |
| `filterable` / `sortable` | repository | fields with indexes (`None`: any) |
| `max_offset` | repository | the deepest page |
| `transaction_scope` | unit of work | `unit_of_work`, `partition` or `none` |
| `max_writes` | unit of work | writes one commit can hold |

A list the store can't run fails with `QueryNotSupported`
([RE-E103](errors.md#re-e103), 400). `details` names the refused `filters`,
`order_by` or `offset` and what the store supports. A resource can allow a
sort the store hasn't indexed: the refusal then explains why.

```python
from resource_engine.capabilities import capability_problems

async with store.unit_of_work() as uow:  # at startup, or in a test
    assert not capability_problems(registry, uow)
```

Declare indexes where the store needs them:

- **DynamoDB:** `DynamoTable(indexes={field: gsi})` for the fields lists
  filter by. Without one, a list scans the table and stops past `max_items`
  (10 000 by default) with `QueryNotSupported`.
- **Firestore:** `sortable=` lists the fields with composite indexes for the
  filters you combine them with.
- **Cosmos DB:** single fields are indexed by default; sorting on several
  needs a composite index (`sortable=` to declare them).

## Row filters

Permission conditions become store filters: a DynamoDB list evaluates them
in memory, Firestore gets `where` filters (`not` pushed into the comparisons,
`exists` as `!= null`), Cosmos DB gets SQL. Conditions a store can't express
(`not exists` in Firestore, two fields compared) fail closed with
`ConditionNotSupported` ([RE-E705](errors.md#re-e705)).

Firestore's `!=` and `not-in` leave out documents that don't have the field.
Translatable fields can't be filtered or sorted in Firestore or Cosmos DB.

## Testing

Each adapter runs `ConditionContract` and `VersionContract` from
`resource_engine.testing.contracts` against its emulator:

```bash
docker compose -f compose.emulators.yaml up -d aws firestore cosmos
uv run pytest -m emulator adapters/resource-engine-aws adapters/resource-engine-gcp adapters/resource-engine-azure
```

Your own store passes the same contracts with a `contract_uow_factory`
fixture built from `contract_registry()`.
