# Translations

An application written in one language can answer, email and document
itself in others. Texts are translated with gettext catalogues: the code
keeps its texts as written, and translators edit one `.po` file per
language.

| What | How it's translated |
|---|---|
| Error answers | Each error has a `title` for people, in the request's language (the engine ships Catalan and Spanish). `message` stays technical and English. |
| Email and document templates | `{% trans %}` and `{{ _("...") }}` in Jinja templates, in the language of each email. |
| Messages in your code | `resource_engine.i18n.gettext` (`_`), `ngettext`, `pgettext`, in the current locale. |
| Functional documentation and its site | Docstrings, descriptions and state names from your catalogue; the generator's own texts (headings, tables) ship with devtools in Catalan and Spanish. |
| Front ends | `resource-engine i18n export` writes a JSON catalogue per language: your messages and the error titles by code. |

Records' fields are what was stored, except the fields a resource declares
translatable (below).

## Translatable data

Some data has a text per language: a product's name, a category's
description, a status label shown to customers. Declare those fields
translatable. They are stored as `{locale: text}` (a `JSON` column in
SQL):

```python
@dataclass
class Product:
    sku: str
    name: dict[str, str] = field(default_factory=dict)


class ProductRead(BaseModel):
    sku: str
    name: str | None  # in the request's language
    name_translations: dict[str, str] = {}  # optional: every language


class ProductResource(Resource):
    translatable = ["name"]
    default_locale = "ca"
```

- **Reading:** `name` is the text in the request's language (from
  `Accept-Language` or the token's `locale` claim). It falls back to the
  base language (`ca-ES` → `ca`), then `default_locale`, then any language
  there is. A `name_translations` field in the read schema gets them all.
- **Writing:** `name` sets the request's language, or `default_locale`, and
  keeps the others. `name_translations` sets several at once, and `null`
  removes a language. Declare it in the create or update schema to accept
  it.
- **Filtering and sorting:** these use the same language and fallbacks: in
  memory, and in SQL as `COALESCE(name->>'ca-ES', name->>'ca', ...)`.

Translatable fields are plain fields to everything else: permissions,
tenancy, the audit trail (which records the whole `{locale: text}` map),
history and the APIs.

## Setting it up

```toml
[tool.resource-engine.i18n]
directory = "invoices/locale"   # <locale>/LC_MESSAGES/messages.po and .mo
source_locale = "ca"            # the language the code's texts are written in
locales = ["ca", "en", "es"]
```

```bash
uv run resource-engine i18n extract    # messages.pot: code, templates, docs texts
uv run resource-engine i18n update     # en/…/messages.po, es/…/messages.po
# translate the .po files (Poedit, Weblate, Crowdin, a text editor)
uv run resource-engine i18n compile    # .po → .mo for the runtime
uv run resource-engine i18n status --strict   # in CI: nothing missing, fuzzy or uncompiled
```

- **extract** reads:
  - the Python code, for `_()`, `gettext()`, `ngettext()` and `pgettext()`;
  - the Jinja templates under `templates/`, for `{% trans %}` and `_()`;
  - the documentation model: docstrings of resources, operations, actions,
    events, hooks and state machines, field and slot descriptions, state
    names.

  A comment starting with `# i18n:` above a call reaches the translators.
  The engine's built-in resources (`authz_*`, `audit_log`, `documents`) keep
  their own English texts.
- **update** creates the `.po` of each locale but the source one, or updates
  it. A text that changed keeps its old translation marked *fuzzy*, which
  gettext doesn't use until someone checks it.
- **compile** writes the `.mo` files the runtime reads. Commit them, or run
  it in the build.
- **status** shows, per locale, how many texts are translated, fuzzy and
  missing. With `--strict` it fails on any gap, so CI catches an
  untranslated text.

## At runtime

```python
from resource_engine.i18n import Translations, set_translations
from resource_engine_fastapi import bearer_actor, install_locale

translations = Translations("invoices/locale", default_locale="ca")
set_translations(translations)  # your catalogue, the engine's behind it
install_locale(app, translations)  # Accept-Language → the request's locale
actor = bearer_actor(authenticator, translations=translations)  # the token's locale claim
```

- **The request's locale:** `Accept-Language` is negotiated against the
  offered locales. `ca-ES` matches `ca`, `pt` matches `pt-BR`, and `q=0`
  refuses a language. If nothing matches, the default locale applies. A
  signed-in user's `locale` claim (the OIDC standard claim) wins over the
  browser when it's offered. Answers carry `Content-Language`.
- **Fallback:** `ca-ES`, then `ca`, then the default locale, then the text
  as written in the code.
- **Elsewhere:** `use_locale("en")` runs a block in a locale (a job, a
  script, a test). The mailer renders each email in its request's `locale`.
- **The engine's catalogue:** error titles are translated by the engine's
  catalogue, keyed by code (`msgctxt`). Your catalogue is consulted first,
  so it can change a title or add a language: add an entry with
  `msgctxt "RE-E102"`.

## Templates

```jinja
{{ _("Factura %(number)s aprovada", number=number) }}

<p>{% trans number=number %}La factura <strong>{{ number }}</strong> ha estat aprovada.{% endtrans %}</p>
```

Pass the catalogue to the renderer:
`JinjaTemplates(..., translations=translations)`. Values inside `{% trans %}`
are escaped in HTML templates like anywhere else. In text templates, prefer
`{{ _("...") }}`. A `{% trans %}` block eats the line break after it
(`trim_blocks`), which joins paragraphs. Per-locale folders (`en/email/...`)
still work, for a template whose layout differs per language. See
[email](email.md#templates).

## Documentation in several languages

`docs generate` writes the docs in the source language, or another with
`--locale en`. `docs site` builds one copy per configured locale (`ca/`,
`en/`, `es/`), each page with a switcher to the same page in the other
languages. The root `index.html` opens the visitor's language when it's
offered, and the first locale otherwise. `--locale` (repeatable) picks
which ones to build.

The application's texts come from its `.po` files, so the docs need no
compile step. Email previews show each language from the compiled
catalogue. The generator's own texts are English, with Catalan and Spanish
shipped. Another language shows them in English until devtools gets that
catalogue.

## Front ends

```bash
uv run resource-engine i18n export --out public/locales
```

This writes `public/locales/<locale>.json`:

```json
{"locale": "en", "messages": {"Factura aprovada": "Invoice approved"},
 "errors": {"RE-E102": "The record does not exist.", "RE-E702": "You are not allowed to do this."}}
```

A front end can show `error.title` from the answer as it is (it's already in
the request's language), or its own text per `code` from the export.

## The example

The invoices example is written in Catalan, with English and Spanish
catalogues in `examples/invoices/locale`. The approval email, the error
titles, the functional docs and the
[published site](https://eloisans.github.io/python-resource-engine/) come in
all three languages.

```bash
curl -s -H "Accept-Language: es" http://127.0.0.1:8000/invoices/999 -H "Authorization: Bearer $TOKEN"
# {"error": {"code": "RE-E102", "title": "El registro no existe.", "message": "..."}}
```
